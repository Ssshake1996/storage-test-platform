语料、Agent 与模型

私有领域里，AI 好不好用，很少只取决于“换一个更强的模型”。更常见的决定因素是：有没有可检索的事实，以及有没有一个 Agent 能在正确的时机，把这些事实组织进模型的窗口。

开场：从聊天到 Agent

Chatbot 的工作方式是问一句、答一句。Agent 的工作方式是一个循环：观察环境 → 组织上下文 → 推理 → 调用工具 → 验证 → 再观察。差别不在文笔，而在它能不能持续接触真实世界，并在每一轮只把“此刻该看的东西”放进模型眼前。

所以这篇讲述不按产品功能清单展开，而按三个角色拆开：

语料

事实与规范

你们系统现在是什么样、规则是什么、哪些坑不能再踩。它是可检索、可引用、可版本管理的材料。

Agent

上下文组织者

通过 Skill、MCP、Spec、工具和 Prompt，决定读什么、读多少、用什么格式、何时停止。

模型

窗口里的推理引擎

只根据当前上下文生成下一步。窗口外的公司知识，对它等于不存在。

贯穿全文的能力公式：

模型智力推理、规划、生成
× 上下文质量相关、及时、干净
× 工具可达范围能读、能查、能验证
× 约束清晰度Spec / 权限 / 验收

在私有场景里，后三项通常比换模型收益更大。模型可以替换；语料、Skill、Spec、权限和工具协议，才是可积累的资产。

核心思想

Agent 通过 Skill、MCP、Spec、工具等机制，从语料和 Prompt 里组织上下文，再交给模型。

三个容易讲错、后面会反复纠正的点：

  • 模型不会自动“知道你们公司”。没被写进训练数据、也没被放进当前上下文的内容，对它等于不存在。
  • Agent 的价值主要不在更会聊天，而在上下文工程。它决定读什么、何时读、读多少、用什么格式、哪些结果回传。
  • 私有领域的护城河在语料与规范，不在通用模型本身。

一、语料：私有领域用 AI 的真正底座

公开互联网上的模型，已经读过大量通用知识。它缺的不是“什么是 HTTP”，而是你们这套存储集群今天的拓扑、昨晚那次故障的结论、以及“这类工单必须先停写再扩容”这种只有内部才成立的约束。

语料比“文档”更宽

显性知识

设计文档、接口约定、故障手册、评审标准、合规条款。写下来了，但常常散落、过期、互相打架。

隐性知识

代码本身、提交历史、工单、评审意见、线上配置、监控与日志。很多“真相”只活在仓库和系统里。

过程知识

怎么排障、怎么发版、什么能做/不能做、谁有权改什么。这是 Agent 最需要、也最容易缺失的一层。

负例与边界

哪些做法看起来对、实际会出事。对私有领域特别重要：通用模型不会替你记住去年那次误删。

为什么私有领域更依赖语料

通用模型擅长公共模式，不擅长你们的命名、拓扑、历史坑和组织流程。幻觉的根因经常不是“模型笨”，而是窗口里没有约束它的事实。它会用一个听起来合理的公共答案，填补私有空白。

微调能改风格和少量领域词，但解决不了“今天这套系统现在是什么样”。检索 + 规范注入，比把所有文档塞进 Prompt 更稳：相关、及时、可审计。

反例。把整本 Wiki 贴进 Prompt；文档和代码互相矛盾却不标明以谁为准；只堆 FAQ，不写约束和验收标准。这些都会让 Agent 更自信地犯错。

好语料的标准

可定位 — 人能找到，Agent 也能按路径、标题、接口名找到。
可执行 — 写的是步骤、约束、验收标准，不是口号。
单一事实来源 — 同一规则只在一处维护。要改接口，先改 spec。
分层 — 总览短，细节按需加载，避免一上来灌进窗口。
带时效 — 过期文档比没有文档更危险。
带权限 — 不是所有语料都该进上下文。

语料如何进入模型

路径典型形态适合什么风险
静态注入 系统提示、项目说明、规格摘要 稳定、短、必须遵守的规则 一长就挤占窗口，且很难针对任务裁剪
按需检索 知识库、代码搜索、文档检索 量大、会变、只在相关时需要的事实 检索错了，模型会顺着错证据推理
工具读取 读文件、查库、看监控、跑测试 需要核实“现在真实状态”的任务 原始输出太长，会污染后续推理
会话记忆 本轮结论、压缩摘要、长期记忆 跨步骤保持目标，避免重复探索 摘要一旦偏了，后面会系统性走偏

语料本身不会自动变成智能。它必须被 Agent 选中、裁剪、引用，才进入模型的工作台。

二、Agent：上下文的组织者

先把定义讲清楚

模型生成 token。
Agent / Harness 决定模型看见什么、能调用什么、何时停止、如何验证。

DeepSeek 的公开表述可以直接用：Agent = Model + Harness。模型是灵魂；Harness 让 Agent 理解环境、使用工具，并在真实环境里持续工作。

一次典型循环两边都能对上：

  1. 收集用户目标与约束。
  2. 选择相关的 Skill、Spec 与语料。
  3. 组装系统提示、工具目录和检索片段。
  4. 模型输出文本或 tool call。
  5. 权限检查后执行工具。
  6. 把结果压缩后写回上下文。
  7. 验证是否完成；否则继续，或把脏活分给子 Agent。

下面用两个公开系统对照：Claude Code 强调分层与保护主上下文；DeepSeek Harness 强调插件化与全程可追踪。共同点都是你的核心思想——运行时在组织上下文，而不是模型在“自动懂业务”。

对照 Claude Code：分层，是为了控制上下文

按公开架构，Claude Code 可以看成五层。每一层都在回答一个问题，也在“花”上下文：

MCP 怎么连到外部系统：API、数据库、私有工具。 工具描述常驻窗口，越多越贵
Skills 怎么把手册变成可复用、按需加载的步骤。典型形态是 SKILL.md。 相关时才注入，成本较低
Agent 主会话谁在干活：读文件、改代码、调用工具、对用户负责。 主窗口会累积对话和工具输出
Subagents 哪些探索不该污染主窗口。子 Agent 自己搜索，只回传结论。 用隔离换主上下文的干净
Agent Teams 跨会话如何协作。成员各有独立上下文，靠消息汇总。 适合并行、长程、多角色

几个值得单独讲的机制：

  • Skill 是可检索的操作手册，不是把全部流程永久写进系统提示。
  • Spec / 项目说明（如 CLAUDE.md、仓库里的单一事实来源文档）应短、硬、可版本管理。稳定规则放这里。
  • 工具让模型接触真实仓库和系统。工具结果会占窗口，所以要切片读、摘要回传。
  • 上下文管理是硬约束。窗口接近上限就要压缩、清场，或把探索丢给子 Agent。

扩展手段也有成本排序，便于取舍：Hooks（几乎不占窗口）→ Skills（低）→ Plugins（中）→ MCP（高，因为 schema 常驻）。私有落地时，不要一上来把所有系统都挂成常驻 MCP。

对照 DeepSeek Harness：一切皆插件，每次运行可追踪

DeepSeek Harness 的官方主线是两句：

Everything is a plugin

能力来自组合

模型、工具、Skill、会话、沙箱、存储、循环、调度、UI 都可以替换重组。换模型不必重写运行时；换工具或循环也不必绑死某一家模型。

Every run is traceable

看见什么都能回放

模型看见的一切写入只追加的 session log：系统提示、推理、工具调用与结果、子 Agent 调度、每一次上下文注入。恢复、分叉、回放、审查走同一条事件流。

这和“私有领域要可审计”直接相关：出了错，先问当时窗口里有什么，而不是只盯最终答案。Trajectory 视图按来源检查记录，就是把上下文工程变成可观察系统。

多种运行模式说明：Agent 的形态可以按任务变，不必只有一种“全能助手”。

Standard

完整编码 Agent：文件、shell、搜索、Skill、规划、子 Agent、工作流。

Code

能力与 Standard 相当，但用生成的代码编排多轮工具调用，减少来回。

Minimal

几乎只留 shell 和编辑器。用来评测模型本身，而不是评测一堆插件。

Creator

检查运行时、试验插件、组新模式。面向做 harness 的人，不是普通聊天。

两边收束成同一张图

机制它在组织什么进入窗口的时机
语料事实、现状、历史坑被检索、被读取、被引用时
Prompt本轮意图和验收标准每一轮用户输入与任务说明
Spec稳定约束与单一事实来源开场注入，或按任务引用
Skill领域打法、可复用步骤相关时按需加载

Agent以上东西的调度、裁剪、验证它不“等于”上下文，它生产上下文
模型在给定窗口上推理和下一步动作只消费当前窗口

Claude Code 教我们：分层 + 按需加载 + 保护主上下文。DeepSeek Harness 教我们：插件化 + 全程可追踪 + Agent = 模型 + 运行时。落地时不必二选一，把这两句话叠在自己的系统上即可。

三、模型：窗口里的推理引擎

模型擅长模式补全、规划草稿、代码和文档生成，以及在给定证据上推理。它不擅长未提供的私有事实、在超长噪音里抓重点、以及不经工具就断言外部世界。

能做

在证据上思考

给你接口定义、报错日志和验收标准，它能提出假设、改代码、写复查清单。

不能做

替你记住公司

没检索到的集群名、没读到的配置、没写进 Spec 的禁令，都会被它用“合理猜测”补上。

可替换

不要把业务焊死在一家模型上

Minimal 模式存在的意义，就是把 harness 减到最小，才能看出模型本身强不强。

上下文窗口就是模型的工作台。工作台上没有的图纸，它只能猜。所以“模型变强”和“上下文变干净”是两件事：前者提高在既有材料上的推理上限，后者决定它到底有没有材料。

这也是为什么评测私有 AI 时，不要只比模型榜单。要同时看：语料能否被找到、Skill 是否在正确任务被加载、工具结果有没有被压缩、主会话有没有被探索过程淹没。

落地：私有领域怎么用这套思想

建议顺序与常见做法相反——先不要纠结选哪家模型。

  1. 先整理语料。规范、接口、故障手册、权限边界，写成 Agent 能按名称和路径检索的形式。过期的标过期，冲突的标明以谁为准。
  2. 再写 Spec / Skill。把“怎么干活”从聊天里抽出来。Spec 放稳定规则；Skill 放按任务加载的打法。
  3. 再接工具 / MCP。让 Agent 能读代码、查系统、跑验证，而不是只根据记忆说话。能用检索和读文件解决的，不要做成常驻 MCP。
  4. 最后才选模型和运行时。Claude Code 这类产品，或 DeepSeek Harness 这类可重组 harness，都是在给模型配组织者。
  5. 用轨迹审查。模型当时看见了什么，比只看最终答案更有用。错了就改语料、改 Skill、改检索，而不是先换模型。
一个贴近本仓库的例子。在存储测试平台里，测试规范、节点状态、知识库文档是语料；planner、executor、tools 是 Agent 侧；模型只在被喂了这些上下文之后，才做分析或修复建议。缺语料时，它会给出一份通用的“看起来很专业”的测试方案，却对不上你们真实的调度和节点模型。

讲述时可用的收束句

模型负责想；语料负责真；Agent 负责把真的东西，在对的时间，放到模型眼前。

三句口诀

  • 没有语料，模型只能猜。
  • 没有 Agent，语料进不了窗口。
  • 没有干净的窗口，再强的模型也会被噪音带偏。
